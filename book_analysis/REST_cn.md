## 论文摘要（第 7 页）
- 万维网的成功主要归因于其软件架构设计满足了 Internet 规模的分布式超媒体系统需求，Web 在 10 年间通过迭代修改标准持续演化，但亟需一个现代架构模型来指导设计、定义与部署（第 7 页）。
- 软件架构研究关注系统划分、组件识别、通信、独立进化等；架构风格是一组命名的、协作的架构约束；作者的工作动机是通过有原则地使用架构约束，为基于网络的应用获得期望的功能、性能和社会学属性（第 7 页）。
- 论文定义了一个通过架构风格理解软件架构的框架，调查了基于网络应用的架构风格并按架构属性分类，提出了 REST 架构风格，并描述了如何用其指导现代 Web 架构的设计与开发，同时总结了从 HTTP/URI 标准应用及部署中得到的经验教训（第 7 页）。

## 绪论（第 8–9 页）
- “形式追随功能”常被忽视，`design-by-buzzword` 多因缺乏对约束背后推理的理解；论文探索软件与网络研究的交叉点，旨在通过架构风格指导架构设计（第 8 页）。
- 早期 Web 被设计为 Internet 规模的分布式超媒体系统，需支持跨组织边界的可伸缩性和独立部署，架构必须在高延迟、多信任边界、大粒度数据对象的环境下工作（第 8 页）。
- 架构不匹配指软件实现因无知或疏忽而违反架构约束；REST 既被用于定义架构改进，也被用于识别架构不匹配（第 9 页）。
- 主要贡献包括：一套相容的术语框架、基于属性的架构风格分类、REST 风格本身，以及该风格在 Web 架构中的应用与评估（第 9 页）。

## 第 1 章 软件架构（第 10–17 页）
### 1.1 运行时抽象
- 软件架构是软件系统在某个操作阶段的运行时元素的抽象，区别于静态的源代码结构；一个系统可有多层抽象和多个操作阶段，每个阶段各有其架构（第 10 页）。
- 架构的核心是抽象原则：通过封装隐藏细节以识别和支持系统属性；架构可递归分解为基本元素（第 10 页）。
- 架构定义基于 Perry 与 Wolf 模型，排除基本原理部分（基本原理属设计文档而非运行时系统），采用组件、连接器、数据三元组（第 10 页）。

### 1.2 元素
#### 1.2.1 组件
- 组件是软件指令和内部状态的抽象单元，通过接口提供数据转换，应基于接口而非实现定义（第 11 页）。
- 组件与连接器的区别：组件在转移数据时可改变数据，连接器则不改变数据（第 11–12 页）。
- 早期模型（如 Garlan 和 Shaw）将架构简化为方框与直线，忽略了数据元素和动态方面，不足以描述基于网络的软件架构（第 11 页）。

#### 1.2.2 连接器
- 连接器是对组件之间通信、协调或合作进行仲裁的抽象机制，在转移数据时不改变数据（第 12 页）。
- 连接器内部可能包含子组件系统进行转换，但外部行为抽象忽略这些细节（第 12 页）。

#### 1.2.3 数据
- 数据是组件通过连接器接收或发送的信息元素（如字节序列、消息、序列化对象），不包括永久驻留在组件中的信息；在基于网络的架构中，数据往往决定一种风格是否合适（第 12 页）。
- Perry 与 Wolf 模型与其他模型的关键区别在于显式包含数据元素，忽略数据会导致架构建模不完整（第 12 页）。

### 1.3 配置
- 配置是运行期间组件、连接器和数据之间的架构关系结构，可视为一组特定约束的集合（第 12 页）。

### 1.4 属性
- 架构属性是由组件、连接器与数据的排列所导致的功能与非功能属性（品质属性）；约束通常通过应用软件工程原则而产生（第 13 页）。
- 架构设计的目标是创造一组架构属性使其形成系统需求的超集（第 13 页）。

### 1.5 风格
- 架构风格是一组协作的架构约束，限制元素的角色/功能及允许存在的关系，为架构分类和定义公共特征提供机制（第 13 页）。

### 1.6 模式和模式语言
- 设计模式是重复出现的系统构造，模式语言是模式的组织化系统；Alexander 的模式概念（作为事件模式与空间约束的共生）在很多方面比面向对象设计模式更接近于软件架构风格（第 14 页）。

### 1.7 视图
- Perry 与 Wolf 提出处理、数据、连接三种视图；4+1 视图模型则使用五类协作视图组织架构描述（第 15 页）。

### 1.8 相关工作
- **设计方法学**：通常只导致一种架构风格，例如 JSD 导致管道和过滤器与过程控制约束的组合（第 15 页）。
- **设计模式手册**：偏重于描述特定问题的解决方案，缺乏不同模式间的比较（第 16 页）。
- **参考模型与 DSSA**：参考模型提供概念框架（如 OMA），DSSA 强调在公共架构领域内重用组件，而非为每个系统选择架构风格（第 16 页）。
- **架构描述语言（ADL）**：如 Darwin、UniCon、Wright、ACME，常引入特定架构假设，可能限制对某些风格的描述能力（第 16–17 页）。
- **形式化架构模型**：CHAM 将架构建模为化学抽象机，Rapide 则基于事件模拟；这些模型关注形式化描述，但各自有适用范围（第 17 页）。

### 1.9 小结
- 引入了一组一致的术语，并强调早期研究常忽略数据作为重要架构元素（第 17 页）。后续两章将聚焦于基于网络的应用架构，并使用基于属性的分类方法调查公共架构风格（第 17 页）。

## 第 2 章 基于网络的应用的架构（第 18–23 页）
### 2.1 范围
- **基于网络 vs. 分布式**：基于网络的架构组件间通信限于消息传递或其等价物；本论文讨论基于网络的系统，不要求对用户完全透明（第 18 页）。
- **应用软件 vs. 网络软件**：讨论局限在“理解业务”的应用软件架构，而非操作系统或网络软件；只有在这一层才能根据用户动作、应用状态位置、有效吞吐量等评估设计权衡（第 18 页）。

### 2.2 评估应用软件架构的设计
- 架构设计的评估可通过检查约束背后的设计原理，并将系统属性与目标应用需求进行比较；第一层评估由功能需求设定（第 18 页）。
- 将架构风格空间视为以“空”风格为根的继承树，理解每种基本风格的属性后，可通过遍历继承树匹配特定应用需求；但一种约束的效果可能抵消其他约束带来的好处（第 19 页）。

### 2.3 关键关注点的架构属性
- **性能（Performance）**：组件交互是决定网络性能与用户可觉察性能的关键。用户可觉察性能取决于延迟与完成时间，二者存在权衡（第 20 页）。网络效率可通过重用缓存、复制数据和移动代码等减少网络使用的方式来提升，性能影响依赖于交互距离（第 21 页）。
- **可伸缩性（Scalability）**：架构在主动配置中支持大量组件或交互的能力；可通过简化组件、分散交互、监视控制等改善，也受交互频率、同步性与信任边界影响（第 21 页）。
- **简单性（Simplicity）**：主要通过分离关注点和应用通用性原则实现；通用性原则应用于连接器便产生了中间件（第 21 页）。
- **可修改性（Modifiability）**：可分解为可进化性（Evolvability，变更实现而不负面影响其他组件）、可扩展性（Extensibility，添加新功能）、可定制性（Customizability，临时规定组件行为）、可配置性（Configurability，部署后修改配置）和可重用性（Reusability）（第 22 页）。
- **可见性（Visibility）**：组件监视或仲裁其他交互的能力；可改善性能（共享缓存）、可伸缩性（分层服务）、可靠性（反射监视）和安全性（防火墙检查）；移动代理风格可能因缺乏可见性引发安全问题（第 22 页）。
- **可移植性（Portability）**：软件能在不同环境运行的能力，可由移动代码风格或标准数据格式导致（第 23 页）。
- **可靠性（Reliability）**：部分故障时系统易受整体故障影响的程度；可通过冗余、监视、可恢复动作提高（第 23 页）。

## 第 3 章 基于网络的架构风格（第 24–36 页）
### 3.1 分类方法学
- 风格选择必须与应用需求一致，分类基于风格应用于原型基于网络超媒体系统时所导致的架构属性；有意排除那些与其他风格结合后不增强通信属性的风格（如黑板）（第 24 页）。
- 评估使用 `+`、`-`、`±` 表示相对影响，可视化采用属性比较表或基于属性的继承关系图（第 24 页）。

### 3.2 数据流风格
- **管道和过滤器（PF）**：每个过滤器独立增量处理数据流，支持重用和可扩展性，但过长管道增加延迟且无法交互（第 25 页）。
- **统一管道和过滤器（UPF）**：强制所有过滤器具有相同接口，增强可组合性但可能降低网络性能（第 26 页）。

### 3.3 复制风格
- **复制仓库（RR）**：通过多个进程提供同一服务改善用户可觉察性能和可伸缩性，需维护一致性（第 26 页）。
- **缓存（$）**：按需复制个别请求结果，提升效率和用户可觉察性能；与客户-无状态-服务器风格结合后成为一种基于网络的风格（第 26 页）。

### 3.4 分层风格
- **客户-服务器（CS）**：通过分离关注点改善可伸缩性和独立进化，基本形式不限制应用状态在客户端和服务器之间的划分（第 27 页）。
- **分层系统（LS）与分层-客户-服务器（LCS）**：通过中间层增强封装和负载均衡，但增加延迟（第 28 页）。
- **客户-无状态-服务器（CSS）**：增加无状态约束，提升可见性、可靠性和可伸缩性，但降低网络性能（第 28 页）。
- **客户-缓存-无状态-服务器（C$SS）**：在 CSS 基础上添加缓存，可消除部分交互（第 28 页）。
- **分层-客户-缓存-无状态-服务器（LC$SS）**：综合 CSS 与 LCS 优点，在多数属性（可伸缩性、进化性等）上获正面影响，但简单性为负；范例系统为 DNS（第 29、36 页）。
- **远程会话（RS）**：应用状态完全保存在服务器上，简化客户端但降低可伸缩性（第 29 页）。
- **远程数据访问（RDA）**：应用状态分布在客户端和服务器上，适合大数据集操作但降低可靠性与可见性（第 29 页）。

### 3.5 移动代码风格
- 所有移动代码风格中一个数据成员被动态转换为组件；位置概念的引入使得在设计层建模组件间交互开销成为可能（第 29–30 页）。
- **虚拟机（VM）**：是所有移动代码风格的基础，提供可移植性和可扩展性但降低可见性（第 30 页）。
- **远程求值（REV）**：将代码发往服务器执行，可定制但缺乏可见性（第 30 页）。
- **按需代码（COD）**：从服务器下载代码扩展客户端，改善可扩展性和可配置性（第 31 页）。
- **LCODC$SS**：COD 与 LC$SS 的组合，代码被视为另一种数据元素（第 31 页）。
- **移动代理（MA）**：移动完整计算组件，灵活性和可伸缩性好，但可见性差（第 31 页）。

### 3.6 点对点风格
- **基于事件的集成（EBI）**：通过事件总线降低耦合，强于可扩展性和可重用性，但可能导致可伸缩性问题（第 32 页）。
- **C2**：结合 EBI 与 LCS，通过异步消息加强底层独立性，在伸缩性和扩展性上表现良好（第 32–33、36 页）。
- **分布式对象（DO）**：封装状态与操作，但标识依赖和可见性差（第 33 页）。
- **被代理的分布式对象（BDO）**：引入名称解析改善重用和进化，但增加网络开销；伸缩性和扩展性好，进化和重用性差（第 33、36 页）。

### 3.7 局限
- 评估专门针对分布式超媒体定制；属性分组可能掩盖特定方面（如可理解性与可验证性）的差异，可进一步分领域细化（第 33 页）。

### 3.8 相关工作
- Shaw 与 Clements 的分类按形状和拓扑组织，未提供基于属性的设计评估，且模糊了风格间的来源关系（第 34 页）。
- 其他相关工作包括分布式编程范例（如 Andrews 的交互范例）、移动代码分类（Fuggetta 等人）和中间件架构研究（Garlan 的架构不匹配分析）（第 35 页）。

## 第 4 章 设计 Web 架构：问题与洞察力（第 37–40 页）
### 4.1 万维网应用领域的需求
- **低门槛**：参与信息创建、阅读和开发都极简单；超媒体作为统一接口，支持灵活的链接和简单搜索（第 37 页）。
- **可扩展性**：系统必须能够应对长期变化，支持渐进和片段的修改，新旧实现共存（第 37–38 页）。
- **分布式超媒体**：需支持大粒度数据转移并将往返延迟降至最低（第 38 页）。
- **Internet 规模**：意味着无法控制的可伸缩性（架构元素必须能在不可预测的负载下正常运作）和独立部署需求，架构必须应对多组织边界和信任边界（第 38 页）。

### 4.2 问题
- 1993 年后 Web 使用激增，早期 HTTP 网络特性差，缓存和中间组件支持不足；IETF 工作组面临定义标准并引入改进而不损害 Web 成功属性的挑战（第 39 页）。

### 4.3 推导方法
- 假设一：早期 Web 架构的设计原理可由一组约束组成的架构风格描述（第 39 页）。
- 假设二：可为此风格添加约束形成新混合风格以更好地反映现代 Web 所需属性（第 40 页）。
- 假设三：修改提议可与更新后的风格对比以在部署前识别冲突；该方法在 6 年间迭代应用于协议标准与软件实现（第 40 页）。

## 第 5 章 表述性状态转移（REST）（第 41–55 页）
### 5.1 推导 REST
- 从“空”风格（无约束）开始，逐步引入约束（第 41 页）。
  - **客户-服务器**：分离用户界面与数据存储，改善可移植性和可伸缩性，支持组件独立进化（第 41 页）。
  - **无状态**：每个请求必须包含理解该请求所需的全部信息，会话状态全存于客户端；提升可见性、可靠性和可伸缩性，但可能增加重复数据开销并降低服务器对一致应用行为的控制（第 42 页）。
  - **缓存**：要求响应数据显式标记为可缓存或不可缓存；可消除部分交互，提高效率与用户可觉察性能，但可能因缓存陈旧数据降低可靠性（第 42 页）。早期 Web（1994 年前）即基于 C$SS 约束集，但缺少统一资源语义（第 43 页）。
  - **统一接口**：REST 区别于其他风格的核心特征，由资源识别、通过表述操作、自描述消息和超媒体作为引擎四个接口约束定义；通过通用性原则简化整体架构并改善交互可见性，代价是降低了特定场景下的效率（第 44 页）。
  - **分层系统**：限制组件只与直接相邻的层交互，封装遗留服务，支持负载均衡与安全策略；增加的开销与延迟可被共享缓存带来的收益所补偿（第 44–45 页）。
  - **按需代码**：可选约束，允许客户端下载并执行代码以扩展功能，改善可扩展性但降低可见性（第 45 页）。
  - **推导小结**：REST 由 CS、LCS、CSS、COD 等风格通过继承和组合约束而成（图 5-9，第 46 页）。

### 5.2 REST 架构的元素
- **数据元素**（第 46–49 页）：REST 通过转移资源表述进行通信，混合了固定映象、封装引擎、原始数据+元数据三种选项。资源是到一组实体概念上的映射 `MR(t)`，分为静态和动态，但映射语义是静态的；资源标识符提供通用接口，支持延迟绑定与内容协商（第 47–48 页）。表述是字节序列加元数据，其媒体类型设计直接影响用户可觉察性能（如增量呈现）（第 48–49 页）。
- **连接器**（第 49–50 页）：包含客户端、服务器、缓存、解析器和隧道等；所有交互均无状态（每个请求包含连接器理解该请求所需的全部信息），接口类似过程调用但参数可作为数据流传递以避免批量处理延迟。
- **组件**（第 50–51 页）：用户代理、来源服务器、网关、代理等通过连接器通信；缓存连接器通过通用接口（而非特定资源的知识）确定可缓存性，组件可通过控制数据覆盖默认行为。

### 5.3 REST 架构的视图
- **过程视图**（第 51–52 页）：展示请求经代理、网关、缓存等中间组件并行路由至源服务器的流程；分层系统允许在通信路径中引入中间组件而不改变组件间接口。
- **连接器视图**（第 52–53 页）：强调通用资源接口使得可用不同协议访问多种服务，但将交互限制在 REST 连接器的标准语义内。
- **数据视图**（第 53–54 页）：将应用建模为超媒体驱动的状态机，用户代理负责保存应用状态，通过选择状态跃迁（链接）推动应用前进；优化的重点在于降低稳定状态之间的延迟，并充分利用缓存。

### 5.4 相关工作
- REST 不同于分布式文件系统或对象系统，与 C2 风格联系密切但增加了中间组件友好的无状态、通用接口与内在缓存支持（第 54 页）。

## 第 6 章 经验与评估（第 56–72 页）
### 6.1 Web 标准化
- 作者自 1993 年起参与 URI、HTTP 标准开发，REST 最初称为“HTTP 对象模型”，后更名为“表述性状态转移”以强调网页作为虚拟状态机的意象；REST 被用作指导框架、描述期望架构、识别问题与比较替代方案（第 56 页）。

### 6.2 将 REST 应用于 URI
- **资源定义与操作**：资源是 URI 标识的概念，客户端只操作表述而非资源本身，从而隐藏实现并支持动态内容选择；远程创作要求创作者获取绑定到底层表述的 URI 集合（第 57–58 页）。
- **语义与实现分离**：服务器端没有资源，只有通过抽象接口提供答案的机制；资源是概念上的映射，特定实现细节均隐藏在 Web 接口之后（第 58 页）。
- **不匹配**：在 URI 中嵌入用户信息以维护会话状态违反无状态约束，导致共享缓存失效并降低可伸缩性；将 Web 视为分布式文件系统会与 REST 资源接口冲突（第 59 页）。

### 6.3 将 REST 应用于 HTTP
- **可扩展性**（第 59–61 页）：通过主/次版本号、可扩展的名字空间规则（方法、状态码、头字段）及升级机制，支持渐进和片段的修改部署，并将消息解析规则与扩展语义分离；引入 Host 头解决虚拟主机问题。
- **自描述消息**（第 61–64 页）：区分内容编码与转移编码；定义与传输独立的语义；避免在协议中硬性限制尺寸并引入过长状态码；通过 Cache-Control、Etag、Vary 等头实现细粒度缓存控制；通过抢先式和反作用式内容协商支持表述选择，并为中间缓存引入透明协商。
- **性能**（第 64 页）：持久连接取代单请求/响应以消除重复 TCP 慢启动，但要求消息自描述且独立于传输；HTTP 不支持回写式缓存因为写入后的元数据可能变化。
- **不匹配**（第 64–67 页）：缺乏普遍的权威/非权威响应区分机制（Warning 头未广泛实现）；Cookie 违反自描述和无状态约束，破坏应用状态管理并引发隐私问题；必需头字段扩展因语法限制成本过高；元数据与消息控制信息混合带来分层困难；MIME 语法冗余且不适合 HTTP；响应与请求的匹配依赖同步连接，尚未内置异步支持。

### 6.4 技术迁移
- **libwww-perl**（第 67 页）：率先实现基于 scheme 动态加载协议的通用接口，展示了通用接口的好处。
- **Apache HTTP 服务器**（第 67–68 页）：作为第一个支持 HTTP/1.1 的主流服务器和参考实现，荣获 ACM 软件系统奖；作者在其中担任“协议警官”以确保实现符合架构原则。
- **整体迁移**（第 68 页）：REST 风格成功指导了新标准的广泛部署，未引发严重问题，且对 Web 健壮性和性能产生积极影响。

### 6.5 架构上的教训
- **基于网络的 API 的优势**（第 68–69 页）：基于网络的 API（标准语义的在线语法）比基于库的 API（共享代码）更具跨平台优势，能避免库分叉与应用惰性。
- **HTTP 并不是 RPC**（第 69–70 页）：RPC 基于特定对象接口，而 HTTP 请求通过具有标准语义的通用接口定向到资源，中间组件可理解并参与处理，这对于 Internet 规模的信息系统至关重要。
- **HTTP 是一种转移协议**（第 70 页）：HTTP 是对资源表述进行转移和操作的转移协议（transfer protocol），而不是传输协议（transport protocol）；将其仅用作穿越防火墙的隧道会丧失架构可见性。
- **媒体类型设计**（第 70–72 页）：REST 要求将应用状态置于表述之中，Cookie 和 frame 等机制因将应用状态置于不应存在的位置而造成混乱与缓存干扰。Java 与 JavaScript 的对比显示，更符合 REST 延迟与可见性约束的媒体类型（如 JavaScript 的增量执行、小尺寸、源码可见）在 Web 中获得了更广泛的采用。

## 结论（第 73–74 页）
- REST 是一组协作的架构约束，通过将约束置于连接器语义上，最小化延迟和网络通信，同时最大化组件实现的独立性和可伸缩性，从而满足 Internet 规模的分布式超媒体需求（第 73 页）。
- 论文贡献包括：架构风格理解框架、基于网络风格分类、REST 风格提出及其在 Web 架构设计与评估中的应用（第 73 页）。
- 现代 Web 是 REST 风格的一个实例；存在可改进领域（如用更高效语法替换 HTTP 的协议族而不丢失架构属性），未来工作将探索可变优先级、服务质量（QoS）及持续数据流等扩展（第 73–74 页）。
- REST 已被验证支撑 Web 从日请求 10 万次增长至 6 亿次（第 74 页）。
